## What shipped

**A console window stopped popping up during normal use.** `os-lint`'s background self-test — a ~10-minute check that runs
automatically when its own freshness marker goes stale — used to spawn a visible `node.exe` console window on Windows. It now
runs with `windowsHide: true`, so it's invisible, as every other background process in this project already was.

**The Performance tab now shows a client's whole exercise history, not just the newest ~200 rows.** The Supabase API caps
every response at 200 rows and says nothing when it cuts a list short. Past that count, alphabetically-later exercises were
silently missing from the list and the tab showed "No sessions logged yet." instead. `_buildExerciseSeries` now pages through
the full history. A new checker, `scripts/check-unbounded-reads.mjs`, runs on every push and fails if a NEW read of one of nine
tables that grow with use (weigh-ins, sessions, sets, check-ins, events…) has no bound narrower than the 200-row cap — the
baseline is pinned at what remained after this fix, so the count can only fall. Its own self-test (45 fixture cases) proves it
can fail: 21 deliberate breakages, all caught.

**A client could no longer be trusted to keep `coach_id` pointed at their real coach.** The live policy `clients_update_own_row`
pinned only `user_id`, so a client's UPDATE could change every other column of their own row too — including `coach_id`. A
client detaching themselves (`coach_id` → NULL) was already known and accepted when the weight-goals feature shipped; pointing
the row at a DIFFERENT coach's id was not covered by that earlier decision, and was confirmed live on 2026-09-26 from a
read-only policy query. Jake chose to close only the "attach to another coach" half.

The fix is a `BEFORE UPDATE OF coach_id` row trigger (`scripts/add-clients-coach-id-guard-2026-09-26.sql`), keyed on
`current_user` rather than a request claim, so the SQL editor, the service role and any admin-owned function are untouched —
only a signed-in `authenticated`/`anon` caller is constrained, and even then only refused when the change isn't the row's own
client detaching. Verified on a PGlite copy of the live schema (including the live `clients` UPDATE policies, added to
`scripts/sql-verify/live-schema.mjs` for this) before Jake ran anything: the verifier first REPRODUCES the hole against the
unpatched schema, then runs the script twice and asserts who is refused and who still works — 35 checks, 10 mutations, all
caught (`scripts/sql-verify/clients-coach-id-guard.verify.mjs` / `.mutations.mjs`). A three-angle review found no blocking
flaw in the SQL itself; it found one in the PROOF — the mutation meant to test the admin exemption had been written so it
disabled the whole guard instead, so nothing was actually testing that exemption — fixed before the commit. Jake applied the
script live on 2026-09-27 and pasted back its read-back, confirming `security_definer=false`, a fixed `search_path`, and
exactly the one new trigger alongside the pre-existing `audit_clients` trigger. `tests/clients-coach-id-guard-2026-09-26.spec.js`
went RED against the live API before the script (a foreign-key error, proving the hole was real) and GREEN after (3/3) —
closure evidence per this project's own ledger rule.

One consequence worth knowing: detaching is now one-way from the API. Before this fix a client could set `coach_id` back
after detaching; now they cannot, and their (former) coach cannot see a coach-less row to re-attach it either. Undoing a
detach is a one-line SQL-editor statement (in the script's own header comment). Nothing in the app does this today.

## Rollback

`git revert 879a95a..6b9f1a2`, then cut and push a new version. Both tags remain immutable once pushed.

**The `clients_guard_coach_id` trigger is not removed by a code revert** — it lives in the database, not in this repo's
deployed code, and nothing in the deployed app depends on it either way. Removing it (if ever wanted) needs its own script:
`drop trigger clients_guard_coach_id on public.clients; drop function public.clients_guard_coach_id();` — reverting the code
in this repo does not do this, and should not: the fix closes a real, confirmed gap and has no known legitimate flow it
breaks.
