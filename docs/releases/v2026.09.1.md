# v2026.09.1 — Library "last used" ordering and search; first tagged release

**Cut:** 2026-09-06
**Commits:** `a59a445..fbf61e4` (18, plus the commit adding these notes)
**Previous release:** none — this is the first tagged release. Everything before it reached the live
site by push-to-master, with no version to name it by.

---

## Scope

Make the Library page usable. Jake's description of it was *"one long string of sessions"*: around 77
templates in one flat alphabetical list, and his method for finding one was *"I scroll till I
recognise it"*.

That last detail is what shaped the release, because **search alone would not have fixed it**. A row
did not carry enough to recognise a session — every row showed the same 💪 icon, the subtitle was the
description or else "5 exercises", and the right-hand side then said "5 ex" again. For a session with
no description the row said the same thing twice and nothing else.

**In:**
- Order the Library by "last used" — the more recent of edited-or-trained.
- Say it on every row.
- A search box that filters as you type.
- The runner recording which template it trained, without which "trained" can never mean anything.

**Deliberately out:**
- **The coach Library page.** It shares the same function today and differs by one line (the title).
  Splitting it before it genuinely diverges is how this codebase grew its duplicate-cluster problem.
  The divergence is now identified and filed — see Known issues.
- **The Exercise Library tab.** Different list, different job, not the complaint.
- **Searching by exercise name.** Would need the query to fetch names it does not currently fetch.
- **Deleting dead sessions.** "Last used 8 months ago" makes them visible; acting on that is separate.

The release also carries the **tag-gated release cycle itself** and a **test-hygiene fix**, both of
which arrived during the work rather than being planned into it. See below.

## What shipped

**For a user:** the Library now puts the sessions you have most recently touched at the top, tells you
on each row when you last used it, and has a search box. "Last used" deliberately means the more
recent of *edited* or *trained* — one label, because whether you last touched a session by editing it
or by training it is not a distinction you care about when hunting for it.

Trained dates start empty and fill from this release forward. Sessions trained in the runner before
now recorded no link back to their template, and that cannot be reconstructed. This is precisely why
the design uses one label instead of two: a separate "Trained" line would have read "Never trained"
across the entire library on day one.

**The description no longer appears on the row.** That is a deliberate trade, not an oversight — the
subtitle now carries the "last used" line, and a row cannot hold both without becoming three lines.

**Technically**, the user-facing change is 130 lines across two modules:

- `js/app-runner.js` — `saveRunnerSession` records `template_id`, and `_runner` carries it through all
  three construction points (fresh start, draft save, draft resume) so a resumed session keeps the
  link. A draft already in a user's browser from the old code still resumes; it resolves to null.
- `js/app-workouts.js` — `renderWorkoutTemplates` fetches templates ordered by `updated_at` and, in a
  second bounded query scoped to those ids, the newest log per template. It merges them to
  `max(edited, trained)`, sorts, and renders `Last used <age>` via a new `_relativeAge` helper.
  `filterTemplates` show/hides already-rendered rows, so typing costs no round trip.

**Also in this release, not part of the original scope:**

- **A tag-gated release cycle.** Before this there was no release concept at all — zero tags, no
  changelog, and every push to master deployed straight to the live beta. Now the checks still run on
  every push but the deploy job fires only on a `v*` tag, and `scripts/release.mjs` refuses to create
  one unless the tree is clean, the notes exist, a review ran after the last commit, `checks.sh`
  passes and the full suite is green.
- **A fix for a long-standing test-flakiness cause.** 39 of 52 row-creating specs clean up inline, so
  cleanup ran only when a test passed — a failing test left debris, debris broke later tests, and
  those failures left more. Traced concretely: one spec had accumulated fourteen identically-named
  fixture rows and its own assertion had become a coin flip. Runs now reap stale fixtures before
  starting, report what they leak at the end, and `checks.sh` refuses a spec that creates rows it
  does not tag.

## Database changes

`scripts/add-template-updated-at-2026-09-04.sql`, applied to production **before** the code shipped.

Adds `workout_templates.updated_at`, backfilled from `created_at` (not `now()`, which would have given
every row the same instant and made the new ordering look sorted while being arbitrary). Maintained by
a `DEFAULT now()` plus two triggers — the load-bearing one being a `security definer` trigger on
`workout_template_exercises`, because editing a session almost never touches the parent row.

**One wrinkle worth recording.** An earlier version of the INSERT half was a `before insert or update`
trigger, briefly live on production on 2026-09-04 and replaced the same day with the DEFAULT. For
about an hour the repo and the database disagreed. It was caught by probing the database rather than
by reading the migration file, which is the only reason it was caught at all.

Documented in the Vault's `data-model.md`.

## Verification

- **Full suite:** 619 passed, **0 failed**, 4 skipped, 28.0m, on the exact code being tagged.
- **Flaky:** `client-workout.spec.js:105` ("client can start and cancel a workout") — failed once,
  passed on retry. Named rather than rounded to "green".
- **checks.sh:** all checks passed.
- **Review:** the pinned three-angle `multi-agent-review` ran TWICE — once on the feature, once on the
  release tooling — plus a whole-branch review and a scoped re-review of the fixes. **None were
  clean.** Every pass found real defects. What they caught is the honest summary of this release:
  - The Library fetch was ordered ALPHABETICALLY under a recency sort, so on an account with ~993
    orphan templates a recently-used session could be cut from the list entirely.
  - Nothing tested the solo path — the one the feature was built for.
  - A `github-pages` environment policy permitted deploys only from branch `master`, with no tag rule.
    The tag-gated workflow would have tagged, pushed, passed every check and then been refused at the
    deploy step — **nothing could have deployed at all.** That policy is not in any repo file; it was
    found via the GitHub API and fixed by adding a `tag: v*` rule.
  - Two of the three new hygiene gates were decorative: a fixture tag inside a COMMENT satisfied one,
    and the release-notes placeholder check caught 8 of 17 placeholders, so a document of pure
    boilerplate would have passed.
  - The reaper's dry run understated its own blast radius, because deleting a tagged client cascades
    to untagged children.
  - The re-review then found two of those fixes incomplete and one newly broken.

**A limit of the verification, stated because this release proved it.** The release receipt
fingerprints the git tree. It cannot see the DATABASE. On 2026-09-04 a trigger on production changed
under a running task and the repo did not know; it was caught by probing the database, not by any
gate. A receipt says "the suite passed on this code", never "the environment is unchanged".

## Known issues carried into this release

- `2026-09-05-coach-library-last-used-under-reports-because-clients-train-clones` (medium) — on the
  COACH view, clients train assigned clones whose logs carry the clone's id, so a master template can
  read "4 months ago" while clients trained it yesterday. Solo is unaffected. Carried because fixing
  it means designing the coach row, which this release deliberately defers.
- `2026-09-05-library-search-term-persists-across-a-view-switch` (low) — a term typed in the coach
  view is still in the box after switching to Personal. Visible, self-correcting, cosmetic.
- `2026-09-05-workout-logs-template-id-is-not-ownership-checked` (low) — verified inert. Carried
  deliberately: the obvious fix puts a refusal risk on every session save to close a gap with no
  demonstrated blast radius.
- **Fixture rows still leak, ~3 per full run** (measured on the tagged code; it was ~13 before the
  reap started running). Bounded rather than fixed: each run now reaps the previous one's debris. The
  root cause — 39 specs cleaning up inline, so cleanup is skipped whenever a test fails — is untouched,
  and the two worst offenders are named in commit `e2cbe85`.
- **The fixture-tag gate cannot prove every insert is tagged**, only that a spec tagging nothing at all
  is caught. Deliberate, and documented in the checker: fixture names flow through variables, so a
  stricter rule would flag correct code and get switched off. The post-run debris count is what
  measures the residue.

## Rollback

The code is a normal revert: `git revert a13ffdf..16a15e8`, then tag and push a new version. Do NOT
delete or move the `v2026.09.1` tag — a released version is immutable, and re-pointing it changes what
that name means for anyone who already has it.

**What cannot be rolled back:** the migration. `workout_templates.updated_at`, its DEFAULT, its two
triggers and its index stay in the database. That is harmless — nothing outside the Library reads the
column, and the triggers only maintain it. The rollback statements are commented at the foot of
`scripts/add-template-updated-at-2026-09-04.sql` if it ever needs to go.

Data written in a new shape: `workout_logs.template_id` is now populated by runner sessions. Reverting
the code stops new rows carrying it; existing values are harmless and worth keeping.
