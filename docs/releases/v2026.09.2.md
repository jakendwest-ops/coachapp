# v2026.09.2 — Fewer taps in the builder, and a propagation prompt that tells the truth

**Cut:** 2026-09-06
**Commits:** `bfaa97b..aa63ef5` (7, plus the commit adding these notes)
**Previous release:** v2026.09.1

## Scope

Sub-project 2 of Jake's three-part scoping request ("reducing the amount of clicks a user needs to
make to create a session, and within the session runner itself"), and the first half of sub-project 3
("moving an exercise up and down in a workout builder … and the adding/removing and saving for
duplicate sessions").

Every change here came from asking which specific moment hurt, then measuring it, rather than reducing
clicks in general.

**In:**
- One tap to repeat a set, not two.
- Tapping a prefilled number selects it, so you overtype instead of deleting first.
- Reordering exercises is instant and asks about duplicate sessions once.
- The propagation prompt states what will NOT change, as well as what will.

**Deliberately out:**
- **Merging split session families.** Diagnosed here (see Database findings) and explicitly not
  attempted — it is unsafe without a session-by-session decision from Jake.
- **The add/remove propagation debounce.** The prompt is now truthful, which matters more than it
  being rarer. Next release.
- **Drag-and-drop reordering.** Agreed as a follow-on to the instant-buttons work, not a replacement.

## What shipped

**Repeating a set costs one tap instead of two.** The set editor had "+ Add set" at the bottom AND a
"Copy set N ↑" button on every row, so repeating a set meant adding a blank row and then filling it. A
four-set exercise was six taps where three will do. There are now two buttons at the bottom —
**Copy previous set** and **+ Add new set** — and none on the rows. Jake chose this over a single
copying button after trying both in a prototype.

**Tapping a prefilled number selects it.** Measured: 143 numeric inputs across the app, 35 of them in
the runner, and zero `onfocus` handlers anywhere. Editing a set that already said 60 meant tapping in,
getting a cursor, and backspacing — one-handed, mid-session. Now you overtype. One document-level
listener, so every numeric input added in future inherits it.

Trade-off, accepted knowingly: on desktop, clicking into the middle of a number to place a cursor now
selects the whole value.

**Reordering is instant.** Every ▲/▼ tap used to run an ownership check, a fetch, two updates, a full
re-fetch and repaint of the session, AND a propagation check. Moving an exercise from eighth to first
was seven taps, seven reloads and seven prompts. The rows now move immediately, the writes still
persist on every swap (nothing is held unsaved), and one repaint plus one prompt happen after the taps
stop.

**The propagation prompt tells the whole truth.** It now names both the copies that will change and
the same-named sessions that will not, and says so with a message rather than silence when nothing is
linked at all. See below for why that matters more than it sounds.

**Machinery, not features:**
- The wrong-escaper check runs at COMMIT, not just at push — after the same mistake shipped into two
  consecutive days' work and was caught both times by a review rather than by any gate.
- A slow suite run now says so, after an identical commit produced 55 failures on a loaded machine and
  0 on an idle one.
- Playwright refuses to collect `zz-*.spec.js`, after two throwaway probes returned three times in one
  day despite being deleted and verified gone.

## Database findings (no change made — read this before "fixing" it later)

Jake reported that duplicate sessions "don't actually update". They don't, and it is not a UI problem.
Measured against his real data:

| Session | Copies | Separate families |
|---|---:|---:|
| Upper Body STR | 13 | 6 |
| Lower Body STR | 14 | 5 |
| Upper STR / Lower PWR | 6 | 4 |
| SkiErg – Threshold Intervals | 24 | 2 |

**18 of his session names are split across families.** Propagation matches copies by `family_id`, so
answering "yes, update the copies" updated a fraction of them.

**This is not a live bug.** `family_id` landed on 2026-08-14 and the library predates it — every one of
the 13 "Upper Body STR" rows was created 13–18 July, so the backfill gave each original its own family.
All six clone paths in the code inherit `family_id` correctly today; each was checked.

**Merging the families was considered and rejected.** The codebase's own dedupe comment records that
Jake has genuinely different 6- and 9-exercise sessions BOTH called "Upper Body STR". Merging makes
editing one silently rewrite the other — worse than today, where it merely does too little. A repair
has to be user-driven, session by session, and is its own piece of work.

## Verification

- **Full suite:** 634 passed, **0 failed**, 4 skipped, **0 flaky**, 29.8m — on the exact code tagged.
- **checks.sh:** all checks passed.
- **Review:** the pinned three-angle `multi-agent-review` ran twice — once on the reorder change
  during development, once on the whole release before tagging — plus a scoped re-review. **Neither
  was clean.**
  - On the reorder change alone: eleven findings across three rounds, including a CRITICAL (wrong
    escaper corrupting names with apostrophes, which would have made propagation silently skip them)
    and a data-integrity bug where a burst of taps after a fork wrote to an orphaned copy.
  - On the release: two more HIGHs. A reorder QUEUED WHILE a fork was in flight still wrote to the
    orphaned master — the earlier fix covered taps arriving after the repaint, not ones captured
    during it. And the pre-commit hook added the previous day could BLOCK A LEGITIMATE COMMIT: its
    handler checker crashed on a missing file and exited 1, the same code the hook reads as "a real
    finding", so renaming a module would have refused the commit with a misleading message and no
    output. Both fixed in `42de1f4`, both proved by neutering.
  - Solo/role review came back genuinely clean: the release adds, changes and removes ZERO
    `coach_id` / `isClientPlan` / `is_personal` gates — the class with four shipped bugs behind it.

**A limit worth restating:** the release receipt fingerprints git. It cannot see the database. A
production trigger changed mid-task on 2026-09-04 and no gate knew.

## Rollback

`git revert bfaa97b..aa63ef5`, then tag and push a new version. Do NOT move or delete the
`v2026.09.2` tag — a released version is immutable.

**Nothing here is irreversible.** No migration, no schema change, and no data was written in a new
shape. The only persistent artefacts are `.suite-duration.json` (git-ignored local timing state) and
the usual `?v=` cache-busts.

**One thing a revert does NOT undo:** the pre-commit hook and `testIgnore` changes are developer
machinery, not shipped code. Reverting them only affects this repo's own gates.
