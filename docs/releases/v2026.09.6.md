# v2026.09.6 — Template builder: staged edits + one Save, instead of writing on every tap

**Cut:** 2026-09-17
**Commits:** `a465694..1c40dad` (47)
**Previous release:** v2026.09.5

---

## Scope

The template builder used to write every exercise add/edit/remove/reorder and every workout
rename straight to the database, which is why the propagation prompt ("apply this to assigned
clients too?") fired once per edit — there was no unsaved-changes state to batch it against. This
release rebuilds the builder around a staged draft: every edit only touches an in-memory
`window._templateDraft` until the coach taps a new "Save workout" button, at which point the whole
batch is diffed and replayed in one pass, and any client/sibling propagation is offered once, for
the full set of changes.

The redesign itself merged cleanly, but three successive rounds of multi-agent review — the
whole-branch review, then a scoped re-review of that review's own fix, then a confirmatory pass on
*that* fix — each turned up real, verified bugs, mostly in the batch/failure/propagation edge cases
a staged-draft model introduces that a write-per-tap model never could. All were fixed rather than
shipped with known holes; see "What shipped" below for the substantive ones.

**In:**
- Four small fixes from a 2026-09-13 walkthrough, unrelated to the builder rework (shipped first,
  same release window): a primary-styled "+ Log weight" button, "My Personal Bests" tab heading
  (now scoped so a coach viewing a client's tab sees "Personal Bests", not "My"), per-program
  comparison scoped to exercises actually logged in the selected block(s), and the template
  editor's "Edit" (rename/describe) button moved beside the workout's own title.
- Template builder: every exercise add/edit/remove/reorder, and every workout rename/description
  edit, now stages into a draft — nothing hits the database until "Save workout" is tapped.
- An explicit "Save workout" button, visible only while the draft is dirty.
- Leaving the builder with unsaved changes prompts once — Save / Discard / Keep editing — instead
  of writing per edit and prompting per edit.
- Client-copy and sibling-session propagation prompts now carry the FULL set of staged changes in
  one pluralized prompt ("3 changes will be applied…"), not one prompt per edit, and the decision
  of which role's rules apply is locked to the role the edit was actually saved under (see below).
- Partial-failure recovery: if a batch Save fails partway through, the draft re-syncs to what
  actually landed in the database and re-stages only the remainder — a retry never re-applies
  changes that already succeeded, and whatever DID succeed still reaches assigned clients and
  sibling weeks rather than being silently stranded.
- The edited template's own row order is now persisted by id, not name — safe even when two
  exercises in the same workout share a name (a warm-up set and a working set of the same
  movement, for instance).
- Save is reentry-guarded against a double-tap, and resolves the real write target (following a
  shared template's fork) and verifies ownership exactly once per Save, never once per queued
  operation.
- Dead code removed: the old settle-debounce reorder subsystem
  (`REORDER_SETTLE_DELAY_MS`/`_reorderSettle`/`_scheduleReorderSettle`/`_cancelReorderSettle`/
  `_reorderChain`), `_afterTemplateExerciseSave`, and `_reorderRowsInDom` — all superseded by the
  staged-draft model.

**Deliberately out** (found during review, triaged as lower-severity, documented rather than
silently dropped — see "Known issues" below): a same-class role-flip-before-dirty-check gap in
`app-dashboard.js`'s `sudoAsClient`/`exitSudo`; a render-timing race that can show the wrong
template's editor after a propagation modal is dismissed mid-navigation; the template editor's
Start button and a few other exit routes still bypass the unsaved-changes prompt entirely; a
removed per-row confirm dialog on Remove (a deliberate product trade-off, not a bug); and several
lower-severity polish items from all three review passes.

## What shipped

**`window._templateDraft` replaces "write on every tap."** Opening a template now snapshots its
exercises and metadata into `window._templateDraft` (deep-cloning `sets_json` so the draft and its
baseline never share mutable state) and every render in the builder reads from the draft, not a
fresh fetch. Add/edit/remove/reorder an exercise, or rename/describe the workout, and only the
draft changes — the database is untouched until Save.

**A pure diff engine replays the whole batch in one pass.** `saveTemplateDraft` resolves the real
write target exactly once (a shared/master template forks on save, never on open — the picker used
to fork it just by being opened), verifies ownership exactly once, then diffs the draft against its
baseline (delete / update / insert / reorder / rename) and replays each op against the target. A
staged add on a template that turns out to be a fork gets its exercise ids remapped so the insert
lands on the fork, not the original it was staged against — and so does every other write in the
same batch, including the new order-persist step below (missed on the first pass at this fix, then
caught and closed by the scoped re-review).

**Save workout button, visible only when dirty.** A direct, explicit affordance for "commit my
edits" that wasn't there before — previously the only way to know an edit had "saved" was that it
already had, silently, the moment you made it.

**Leaving with unsaved changes prompts once — and switching between Coach/Personal view does too.**
`navigate()` checks `_templateDraftIsDirty()` before every navigation (back button, tab switch, or
any other exit path) and raises a single Save / Discard / Keep-editing prompt. `switchView` (the
Coach/Personal view switcher) now runs the same check *before* changing which role is active,
rather than flipping the role first and letting a Save triggered afterward run under the new role.
That reordering closed the review's most serious finding: a Personal-view edit saved via a
switch-to-Coach tap could previously end up offering to write into a real client's plan (or the
reverse could silently skip a client that should have been offered the update). Reordering
`switchView` alone turned out not to fully close it, though — the batch write's own baseline reset
(the duplicate-insert fix below) makes the draft look clean the moment the writes land, reopening a
narrower timing window during the several awaited round-trips propagation itself takes. The role
the edit is being saved under is now snapshotted once, before any of those round-trips start, and
threaded explicitly through the propagation decision, so a same-tab role switch mid-save can no
longer change which role's rules apply to an edit already in flight.

**Propagation is offered once, for everything that changed.** `_showClientCopyPropagateModal` and
its sibling-session counterpart now take an array of changes and build one pluralized summary
("2 changes will be applied to their copies too?") instead of firing per-edit with singular,
per-change wording.

**Partial-failure recovery re-syncs, not re-applies blindly — and no longer strands what already
succeeded.** If a batch Save fails partway through (say, the third of five queued deletes is
refused), the draft re-fetches the template's real current state, folds it in as the new baseline,
and re-stages only the portion of the original batch that hadn't yet reached the database — keyed
by a per-op-type success count, not by exercise name (names aren't guaranteed unique within a
template, so a name match could silently re-stage the wrong one of two identically-named rows). The
recovery re-stage also only ever copies the staged fields onto the freshly-fetched row, never its
id — an earlier cut used a blanket object copy that could overwrite a freshly-forked row's real id
with a stale pre-fork one, so a later retry would delete the wrong (real) exercise. And whatever DID
commit before the failure is now still offered to assigned clients and sibling weeks, rather than
being silently and permanently stranded because a retry's fresh baseline no longer contains it.

**The edited template's own reorder is id-keyed, not name-keyed.** Sibling/client-copy propagation
of a reorder is still necessarily name-keyed (a copy doesn't share ids with its source), but the
template actually being saved has real ids in hand — reusing the name-keyed helper for its own
order collapsed two same-named rows onto one sort rank and silently wrote nothing while reporting
success. A new `_persistOwnTemplateOrder` fixes this for the target template specifically.

**A propagation-triggered repaint can no longer clobber an in-progress recovery draft.**
`openTemplate` now refuses to rebuild `window._templateDraft` when it's already set for the same
template id and still genuinely dirty. Several "nothing to propagate" branches call `openTemplate`
fire-and-forget after a Save; without this guard, that repaint (a real, un-awaited network
round-trip) could land moments after a partial-failure Save returned, silently discarding the
just-rebuilt recovery draft and its still-pending changes with no signal to the user.

**Reentry guard + once-per-Save ownership/target resolution.** `saveTemplateDraft` is wrapped in
`guardReentry` (a double-tap could otherwise fork the same shared template twice, or double-write
every staged change), and both the write-target resolution and the ownership check happen exactly
once per Save call — never once per queued operation, which would have risked forking a still-
shared template a second time mid-batch.

**Dead code deleted.** The old per-tap reorder-settle debounce subsystem no longer has anything to
debounce (reorders are staged now, not written live), so it and its two now-meaningless tests
(`_afterTemplateExerciseSave`, `_reorderRowsInDom`) were removed rather than left inert.

## Verification

- **Full suite:** **675 passed / 0 failed / 0 flaky (32.9m)**, run on the exact commit pushed to
  `origin/master` (`1c40dad`), after GitHub's own CI run against the same commit had already
  completed (avoiding the two-runs-one-test-account contention `tests/global-setup.js` refuses). An
  earlier same-commit run showed 2 failures in `tests/library-last-used-2026-09-04.spec.js`
  ("Last used today" vs "yesterday") — traced to a genuine but unrelated pre-existing fragility: the
  fixture computes "today" via `new Date().toISOString()` (UTC), and that run happened to fall
  inside the ~1-hour daily window (Europe/London BST, UTC+1) where the UTC calendar date and the
  local one disagree. Confirmed by checking system local vs UTC time at the moment of failure
  (exactly a 1-hour, cross-date offset) and by a clean re-run once the window closed.
- **checks.sh:** failed repeatedly during development, on real, in-scope findings each time — never
  forced through, never silenced by weakening a check. Two full rounds: the first while landing the
  staged-draft model itself (a `waitForTimeout` ratchet, a cross-module backward reference, and a
  spec-teardown-hygiene ratchet, all traced to this branch's own new test file and either fixed for
  real or, for one fault-injection mock, a deliberately raised and documented baseline), and a
  second when a deliberate, necessary settle-wait was added during the review-fix rounds (documented
  in `scripts/count-baseline.json`, raised by exactly 1 with the reasoning inline). Clean
  (`=== All checks passed. ===`) on the final committed state.
- **Node unit tests:** 50 pass, 0 fail (9 suites).
- **Review:** three full rounds, each on the previous round's own diff, not re-litigating what the
  prior round already covered:
  1. Whole-branch review (3 fixed angles: security/scoping, solo-mode, duplicates/regressions) —
     4 Critical/Important findings, all fixed.
  2. Scoped re-review of that fix — found the role-snapshot gap described above plus a second real
     bug (the order-persist fix's own id-remapping was itself incomplete on the first pass), both
     fixed.
  3. Confirmatory re-review of *that* fix, narrowly scoped to just the newest changes — found one
     more real bug, in a new test rather than production code (a `page.waitForFunction` call with an
     async predicate that doesn't actually poll, so it could only have passed by lucky timing);
     fixed by switching to `expect.poll`, then confirmed with 3 consecutive clean isolated runs.
  No findings from any round were shipped unfixed; lower-severity items from all three rounds are
  listed under "Known issues" below rather than silently dropped.
- **Test maintenance:** a now-vacuous regression test (`tests/personal-programs.spec.js`) was
  silently passing for the wrong reason — it set the OLD singular `window._lastExerciseChange`
  global, which production no longer reads, so its `_checkClientPlanPropagation` call ran with an
  empty changes array and both assertions passed by doing nothing. Fixed to pass the change set
  directly, matching how `saveTemplateDraft` itself now calls that function. A second, similar
  latent issue in `tests/session-identity-2026-08-14.spec.js` (a singular change object passed where
  an array is now expected) was also fixed, though it remains dormant on its own fixture either way.

- **`/deploy-check`:** carried from v2026.09.5 — no infra, RLS, bucket, redirect-URL or schema
  change since; this release is client-side JS + tests only.

## Known issues carried into this release

- `2026-09-05-coach-library-last-used-under-reports-because-clients-train-clones` (medium) — unchanged.
- `2026-09-05-library-search-term-persists-across-a-view-switch` (low) — unchanged.
- `2026-09-05-workout-logs-template-id-is-not-ownership-checked` (low) — verified inert, unchanged.
- `2026-09-06-machine-load-makes-the-suite-fake-a-catastrophic-regression` (medium) — unchanged;
  directly relevant this release, since an early full-suite run on the merged commit showed 17
  failures across unrelated subsystems that a clean re-run of a representative sample confirmed
  were contamination, not real regressions, and one test-file re-run this session showed a single
  transient failure that passed cleanly on 3 immediate isolated re-runs.
- **New, low-severity, worth a ledger row of its own:** `tests/library-last-used-2026-09-04.spec.js`
  computes "today" via `new Date().toISOString()` (UTC) but the app's own "Last used today/yesterday"
  wording is evaluated against the local calendar day — so the two spec tests keyed on "today" fail
  deterministically during the daily ~1-hour window (Europe/London BST, UTC+1) where the UTC and
  local dates disagree, roughly local midnight to 01:00. Not a product bug (no user-facing behavior
  is wrong — the fixture's own "today" is simply computed in the wrong timezone), but worth fixing
  in the test the next time someone is in that file, since it will keep failing in that same window
  indefinitely otherwise.
- **New this release, found by the review rounds above and deliberately deferred (not blocking, all
  documented in this branch's own SDD ledger for a future follow-up):**
  - `app-dashboard.js`'s `sudoAsClient`/`exitSudo` flip `currentProfile.role` before checking for a
    dirty template draft — the same shape `switchView` had. Narrower exposure: `'client'` role
    doesn't trip the solo-suppression the way `'solo'` does, so the real-client prompt still
    correctly appears; the role-snapshot fix above also incidentally closes the actual
    write/disclosure decision for this path, leaving only which role's *screen* renders next as the
    open question.
  - A propagation-dismissal modal can resolve `_waitForPropagationModalsToClear` on its own removal
    from the DOM, before the dismissal handler's own async work (and a possible role flip) has
    actually finished — so the wrong template's editor can render under the wrong role after
    dismissing a propagation prompt mid-navigation. The write/disclosure decision itself is safe
    regardless (per the role-snapshot fix), so this is a confusing-render regression, not a
    data-safety one.
  - The template editor's ▶ Start button (and a few other exit routes) still bypass the
    unsaved-changes prompt entirely — staged edits are not lost, just silently left staged while the
    user trains the pre-edit version of the workout.
  - Several lower-severity items from all three review rounds: a triplicated leave-guard block
    across `app-core.js` (×2) and `app-workouts.js`; no defensive filtering of a `null` id in the
    (very narrow, already fails-safe) case a draft row vanishes mid-save; a duplicate-`order_index`
    edge case if a partial `_persistOwnTemplateOrder` run is later followed by a fork of the same
    template; a stale header comment in `tests/reorder-instant-2026-09-06.spec.js` describing the
    deleted debounce model.
- The propagation prompt firing once per Save (rather than per-edit) was the whole point of this
  release for the template builder — the equivalent redesign for program-workout edits (the
  `2026-09-13` walkthrough's second ask) is not part of this release.
