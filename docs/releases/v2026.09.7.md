## What shipped

**The Progress → Benchmarks tab is gone.** Jake asked twice, after being shown it was the only
Progress-page view of `performance_logs` (cardio/benchmark/body-metric records) — a different table
from Personal Bests' `client_1rms`, so not a true duplicate, but nothing calculates from it. A client
now sees those records only on the dashboard Benchmarks cards (the four most recently logged); their
coach still sees all of them on the client's Performance tab. Fixing the tab surfaced a real bug in
those dashboard cards: they picked the "best" record by category instead of by unit, so a lighter
lift logged in a different unit could show as the record (100kg vs 220lbs showing 220lbs as the
best). Both dashboards now share one `_bestPerfLog`-based helper.

**Automatic error capture.** `log.error` calls and two global handlers (`window.onerror`,
`unhandledrejection`) now write to a new `app_errors` table instead of only the user's own browser
console — closing a beta gap from 2026-07-11 where a tester's crash was invisible unless
self-reported. The owner reads them, grouped, in a Settings card. The privacy policy's promise that
error logs hold "only internal IDs and timestamps" is held to in substance: a report is a code, a
code location, and technical context — never an error message string, a name, an email, or a health
value. Two independent reviewers found the rate limit (60 reports/user/hour) was evadable — a client
could set their own `created_at` and back-date past it — before this shipped; fixed with a
server-side trigger that sets `created_at` itself. A companion Send-feedback link opens the user's own
email client with a pre-filled address; nothing typed into it is stored by this app.

**Reads of a growing table no longer silently truncate — on the sites this release reaches.** The
Supabase API returns at most 200 rows per request regardless of what's asked for, and says nothing
when it cuts a list short. Sixteen queries in six functions assumed otherwise; each had passed every
test it had, because no fixture holds 200 rows. `_fetchAllRows` (`js/app-core.js`) pages through a
table properly and returns `{ data: null, error }` on a failed page rather than a partial list. The
data export used to tolerate a failed read (including silently shipping a bundle with a missing
profile section) — it now throws, and `downloadMyData` reports "Export failed" rather than a false
success. `684c7fa`'s own commit message is explicit that this did not reach every unbounded read in
the app — see "Known issues" below for what's still open, including one still-live bug in My
Progress → Strength.

**A per-coach summary SQL view, verified before it ran live.** `coach_client_summary` computes each
client's session counts (7-day, 28-day), last-session date and last-weigh-in date server-side, so the
coach dashboard and client list stay correct past the 200-row cap without paging through raw logs
client-side. It's `security_invoker`, so the base tables' RLS applies to whoever queries it, and it
carries its own `coach_id = auth.uid()` filter as a second wall. Before Jake ran the migration live,
`scripts/sql-verify/` reproduced the live schema (tables, indexes, RLS policies) in an in-memory
Postgres and ran 47 checks plus 9 deliberate breakages against it — three mutations a first draft of
the verifier missed are why the mutation suite exists at all. The verifier's own README is explicit
about what a pass does *not* prove: INSERT/UPDATE/DELETE policies, concurrency, triggers, and the
PostgREST layer are all out of its reach and covered instead by
`tests/coach-client-summary-2026-09-21.spec.js` against the real, deployed API.

**Product-review fix batch (R1).** `saveNewTemplate` now verifies the programme/phase pair belongs to
the caller before its first write, closing an ownership gap found by the 2026-09-18 weekly full-file
review. Stored periodization config values are now escaped on render — the ninth instance of this
project's recurring unescaped-stored-attribute XSS class, closed with the same shared escaper and the
escaping checker (`scripts/check-escaping.mjs`) taught to catch this shape too. "Copy to coaching
programs" now refuses unless the current view is a coaching one, closing the bug where a solo user
could create a copy they could never see, open, or delete. Check-in stress and soreness scores are
now scored the direction real wellness scales use — low is good — after shipping inverted. The
workout runner requests a screen wake lock during a session and a rest timer now survives the phone
locking, instead of the runner silently losing time.

**Runner PRs now check full history.** "New PR" claims previously compared against a recent, possibly
truncated slice of past sessions for that lift rather than the true all-time best, so a genuine
personal record over a much older number could go unflagged, or — depending on which slice happened
to be in view — an old number could be re-claimed as new. It now checks the complete logged history.

**The duplicate-exercise bug.** Full root cause, fix, and verification: see the "Fixed propagated
exercise adds" section of `docs/bugs/2026-09-20-adding-an-exercise-to-a-program-workout-duplicates-it-several-times.md`.
In short — propagating an added exercise to another workout wrote the target's own id back onto the
row it had just inserted into the *edited* workout, so every target got nothing and the edited
workout got a duplicate per target, while reporting success throughout. A new
`_propagationRowFields` helper strips the edited workout's own id/position from a change row before
a target's own id and position are set, guaranteed to be set last. This also closes the same
never-triggered risk in the sibling update-propagation path.

## Rollback

`git revert c88057f..79feb38`, then cut and push a new version. Both tags remain immutable once
pushed.

**Not fully reversible without care.** The `app_errors` and `coach_client_summary` migrations are
additive (a new table, a new view, new indexes) — reverting the code does not drop them, and they can
be left in place harmlessly. `downloadMyData` now throwing on a failed paged read, instead of
returning a partial bundle, is a deliberate behavior change from v2026.09.6 that a revert would also
undo — see `docs/decisions.md`'s 2026-09-20 entry for why that reversal is the one this project chose
not to make lightly.
