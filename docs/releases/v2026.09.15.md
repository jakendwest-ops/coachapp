**In:**
- The program page opens with an overview: the name, "N phases · W weeks · a-b sessions a week", the description clamped to two lines
  (Show more only when it is really cut off), the one main button, and a bar with a block per phase (as wide as its weeks, blue for a
  %-based phase, green for an RPE-based one, grey for none; tap a block to jump to that phase).
- Each phase is a fold-up card: one line (number, name, weeks, sessions a week, method chip), the first one open. A folded card holds none of
  the builder, so a 12-phase program no longer draws 12 weeks at once.
- Inside an open phase: the periodization row (Add / Edit periodization and Generate weeks stay visible), the week tabs with a ⋯ for the
  week, and - on a phone - the seven days as slim rows (a rest day is one thin line with + Add). On a computer the seven-column week is
  unchanged.
- Edit / Remove a phase and Duplicate / Delete a week moved behind ⋯ sheets (the same pattern as the workout screen's ⋯ menu), so a stray
  tap cannot delete anything. Units moved into Manage. "Add a second workout on this day" moved into the opened workout's panel.
- Periodization by RPE: a "% of 1RM | RPE" switch in the periodization dialog, one method per phase. RPE Linear is start RPE to end RPE in
  half points with an optional deload week at its own RPE; RPE Undulating gives Heavy / Moderate / Light an RPE. Generate weeks steps the
  RPE (or RIR, converted: RIR = 10 - RPE) of every Week-1 set that already has one; weights and "% of today's top set" back-offs never
  change. The dialog previews each week ("Week 1 stays as you typed it") and says how many Week-1 sets will step, warning when none can or
  when they sit at different values. Existing phases stay on %.
- The page opens the phase **your plan is in**, not always the first (Jake's answer, 2026-10-04: "open current phase"). The phase is the one
  today falls in for the plan the viewer follows themselves - weeks counted Monday to Sunday from the start date, by the same function the
  dashboard's program tile now uses, so for a running plan the two cannot disagree - and it carries a small "Now" badge, folded or open. Not following the
  program, a plan that has not started, or one that has finished: the first phase opens, as before, and nothing says Now. What you open or
  fold afterwards is still kept.
- The Undulating "Reps" boxes are gone (Jake's answer, 2026-10-04: "remove"). They were saved but never used when weeks were generated, so
  they only looked like they did something. The tier's %1RM (or RPE) is the whole setting now. A tier's old typed reps are dropped from the
  stored config the next time the dialog is saved (nothing ever read them).
- A guard against a class of bug found on the way: a saved value named like a function replaces the function (see below).
- Test housekeeping, no app change: the cleanup block of one older test (`session-identity-2026-08-14.spec.js`, "renaming FROM a week copy")
  used the wrong keys and left two `[E2E] dbl ...` templates in the test account after every full run; fixed, and the run's debris report
  now says "No debris found" for it.

## What shipped

Plain English first. **Programs:** open a program and the top tells you what it is at a glance, with a coloured bar showing the phases; each
phase is a one-line card you tap to open; inside, the week's days are short rows, and the rarely used buttons (Edit, Remove, Duplicate week,
Delete week) are tucked behind a ⋯ so they cannot be hit by accident. If you are following the program yourself, it opens on the phase you
are in this week and marks it "Now" - not always the first phase. **Periodization:** the window now asks "% of 1RM or RPE?". Pick RPE,
set a start and an end (say 7 to 9), and Generate weeks gives week 2 an RPE of 7.5, week 3 of 8.5 and week 4 of 9, on every set that has an
RPE in week 1, leaving the weights alone. The "Reps" boxes on the Undulating (Heavy / Moderate / Light) tiers are gone: they never changed a
generated week, so they were only a place to type something that did nothing.

Technical detail is in `docs/decisions.md` (the 2026-10-04 entry on this change) and the two bug rows. In short: `openProgram` builds the
overview and `_pgmCardHtml` cards from `_pgmOpenState` / `_pgmSegHtml`; `_renderPhaseBody` paints an open card from the cached
`_builderWeekData`; the ⋯ sheets are `_pgmSheet` with the context in `window._pgmMenu`; periodization adds `_pzBasis`, `_computePeriodizedRpe`,
`_applyWaveRpe`, `_pzWeek1Report`, `_pzSnapshot`, `_pzRefreshPreview`, with the dialog's current method in `window._pzMethod`. The method is
stored as `basis: 'rpe'` inside the phase's untyped `periodization_config`. The phase a plan is in is `_programPhaseAt` (in
`app-dashboard.js`, shared with the program tile) behind `_pgmCurrentPhaseId` in `openProgram`, which hands it to `_pgmOpenState` and the
"Now" badge (`window._pgmNowId`). Cache-busting versions: app-programs 71, app-dashboard 32, main.css 30 (the live site has 68, 31 and 27).

One bug worth knowing about, found only by running the real browser: the dialog first kept its method in `window._pzBasis` while a function
`_pzBasis()` read a phase's method - the window property replaced the function, so after the dialog was opened once the page died with
"_pzBasis is not a function". Renamed, and `tests-node/window-shadow.test.mjs` now scans every script for a `window.x =` that shares a
function's name (it found no other).

## Database changes

None. `program_phases.periodization_config` is an existing untyped jsonb column; the RPE method adds a `basis` key inside it only when a coach
saves an RPE phase. A phase without the key is read as %, exactly as before, and a % save writes the shape it always did.

## Known issues carried into this release

- None of the new screens has been looked at on Jake's phone with his real six-phase program; they were tested with example data, the test
  accounts, and screenshots at 480, 320 and 1280 px.
- "The phase your plan is in" follows the viewer's OWN record of the program. A coach looking at a program they built for a client sees the
  first phase open (the coach is not the one following it); only a program the viewer follows themselves opens on its current phase.
- The runner files a session under the UTC day, not the local day (`docs/bugs/2026-10-04-runner-saves-the-session-date-as-the-utc-day.md`).
- "Up next" follows the calendar: a workout done on another day or in a swapped order is not matched to its slot
  (`docs/bugs/2026-10-04-workouts-up-next-card-does-not-name-the-workout.md`).
- `progress-trend.spec.js:5` (the resting-HR chart on the Body tab) is a fixed-sleep race that fails once in a while and passes on retry
  (`docs/technical-debt.md`). It did not flake in this release's run.
- The one flaky test of this release's run was `_debug-adhoc-audit.spec.js` ("W3: sign out via Settings at 390px"): a gitignored, untracked
  throwaway probe from the 2026-09-27 audit (its header says "Delete after running") that exists only on the machine that cut the release.
  It signs the PT out, fails once and passes on retry. It is not in the repo and does not run in CI; deleting it is Jake's call (it is the

## Rollback

Tag the previous version's commit (`v2026.09.14`, `fb29e45`) and push it, or revert the range `v2026.09.14..HEAD`. Nothing in this release
changes the database. The only data written in a new shape is `basis: 'rpe'` inside the config of a phase a coach saves as RPE; after a
rollback the old code would read that phase as Linear with no % numbers, so Generate weeks would copy Week 1 unchanged until the phase is
switched back to %. The other change to stored data goes the same way: saving an Undulating % phase now writes only each tier's %1RM, so a
rollback would show the old dialog's default Reps text (3-5, 6-8, 10-12) in place of whatever had been typed - text that never affected a
generated week. Nothing is lost.
