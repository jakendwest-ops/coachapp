# runner's pre-Start cardio screen showed a stale work/rest duration for interval exercises

✅ **FIXED SAME SESSION 2026-08-08 — runner's pre-Start cardio screen showed a stale work/rest duration for interval exercises.** Jake, live, with screenshots: the Workouts-page preview correctly showed his SkiErg interval prescribed at 20:00 work / 5:00 rest, but starting the runner showed "Target: 10:00 / Rest: 3:00" — his own hypothesis: "holding on to the old data that was in this session, as that work duration was 10:00." **Root-caused via a live diagnostic query he ran and pasted back** (not guessed): the exercise's `sets_json` block genuinely carried BOTH pairs at once — `workSecs:1200/restSecs:300` (current, matching the preview) AND `duration:"10:00"`/`restMin:"3:00"` (stale, matching what the runner showed). The interval editor's own inputs (`ts-worksecs-0`/`ts-restsecs-0`) only ever write `workSecs`/`restSecs` — `duration`/`restMin` aren't rendered for interval type, so `flushTemplateSets`'s "missing input leaves the value alone" rule (its own comment) means they've silently kept whatever they were from before this block was last edited via the interval editor, with nothing to ever clear them. The runner's pre-Start cardio card (`app-runner.js`, shared between plain cardio and intervals since both report `exercise_type:'cardio'`) read `tgt.duration`/`tgt.restMin` unconditionally — the legacy fields, not the current ones. **Confirmed NOT a functional bug**: `startCardioTimer()` already forks interval exercises to the phase-walk engine (`_startPhaseAt`/`_expandIntervalBlock`), which correctly uses `workSecs`/`restSecs` — so the actual timer that ran was always the right length; only the display before you tapped Start was wrong. Fixed by branching on `_isIntervalExercise(ex)` and reading `workSecs`/`restSecs` (via `fmtRestCountdown`) instead, for the target chips and the duration-input pre-fill. Red→green test added (`tests/intervals-redesign-2026-07-25.spec.js`, reproduces Jake's exact field shape, verified failing against pre-fix code by temporarily reverting the file to HEAD and restoring). Full suite 342 passed / 5 pre-existing `client-workout.spec.js` failures (unchanged baseline) / 1 flaky (same file, known class) / 2 skipped. mobile-checked at 390×844 (screenshot confirmed "Target: 20:00 · Rest: 5:00" and the Duration input pre-filled 20:00, no stale values anywhere). Multi-agent review (3 angles) clean; Agent C's one finding (the Target chip lacked the `!== '0:00'` guard the Rest chip already had, for a genuinely-zeroed work duration) was real and fixed same commit — verified by re-running the full intervals suite (50/50 still green).
