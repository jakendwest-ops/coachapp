# Server-side "today" is still the UTC day (the coach summary view and the plan-restart function)

## Where it came from

The app side of "today taken from the UTC day" was fixed on master 2026-10-17 ([2026-10-13 row](2026-10-13-dates-defaulted-from-the-utc-day-are-wrong-outside-utc.md), [2026-10-04 row](2026-10-04-runner-saves-the-session-date-as-the-utc-day.md)). A session now carries the day the person started it, on THEIR clock. Two objects in the database were written against the old stamp.

## 1. `coach_client_summary` hides a session dated "tomorrow" in UTC

`scripts/add-coach-client-summary-2026-09-20.sql` lines 105, 110, 114 and 115 cap and window on `(now() at time zone 'utc')::date`, and ignore a log dated after it (its header says a future-dated log is a typo). With the fix, a session started at 00:30 BST on 16 July is dated `2026-07-16` while the UTC date is `2026-07-15`, so `16 <= 15` is false and the row is dropped from `last_session_date`, `sessions_7d` and `sessions_28d` until 01:00 BST. Readers: the Clients list label (`js/app-clients.js:137`) and the dashboard "Needs attention" (`js/app-dashboard.js:541`). Window: 1 hour in the UK, 2 in central Europe, most of a morning in Australia or New Zealand; west of UTC the cap does not bite. Before the fix the same session was stored as the 15th, so it showed, a day early.

**Script written 2026-10-17:** `scripts/fix-coach-client-summary-utc-cap-2026-10-17.sql` makes both caps `+ 1` day (it differs from the live view statement by exactly those two lines; every zone up to UTC+14 is covered and the T+400 typo is still excluded). Verifier `scripts/sql-verify/coach-client-summary-utc-cap.verify.mjs` (25 checks: the bug reproduces on the original first, then the session shows, two days ahead and a year ahead still do not, the window edges did not move, the same 19 columns, `security_invoker` and the privileges kept, other coach / client / no identity / anon refused) and eight breakages in its `.mutations.mjs`, all caught. Run in rule 9m of `checks.sh`. Run by Jake 2026-10-17; its read-back matched.

## 2. `assign_program()` stamps `ended_at = current_date` on a restart

`scripts/add-assign-program-rpc-2026-09-27.sql` line 101 (and the column default in `add-program-blocks-2026-08-15.sql:57`) write the server's date, which is the UTC day. The JS twin `_archiveAssignmentBlock` (`js/app-programs.js:372`) now writes the local day, and its comment says "change one, change the other". In the same 00:00 to 01:00 BST window the two archive copies of a block's end date differ by a day. The only reader (`_loadProgramBlocks`) tolerates a one-day skew, so this is cosmetic history. The fix is a `p_today date` argument the browser fills with `_ymdLocal(new Date())` (one caller, `_assignProgramTx`, `js/app-programs.js`). **Script written 2026-10-17:** `scripts/fix-assign-program-restart-date-2026-10-17.sql` creates the five-argument function FIRST and drops the old four-argument one SECOND (two functions of one name would make the API refuse every call as ambiguous; this order never leaves none); it differs from the live function by exactly three lines; `p_today` is optional (without it the function behaves as before) and clamped to a day either side of the server date, so a wrong device clock cannot write a wild date. Verifier `scripts/sql-verify/assign-program-today.verify.mjs` (59 checks) installs the original function first, then runs EVERY original check against the new one, plus the new behaviour and the rollback. **Order of release:** the SQL first, then the browser line; a browser that sends `p_today` to the old function is refused and no plan can be assigned.

**Closes when:** Jake has decided on both changes and run the SQL that was verified locally first (a verifier plus a mutation under scripts/sql-verify/, the 00:30 BST case failing with the UTC day put back), and the coach summary shows a session started at 00:30 local time on the Clients list straight away.

## Not tested

Both fixes are covered by live specs (see status_detail), but none was run red against the old database object (that would mean undoing the live change; the local verifiers reproduce the old behaviour). Not tested: a real phone, or a restart / a session in the real first hour after midnight. The view's local verifier checks the two changed caps, the window edges and who can read it, not the values of the unchanged weigh-in, check-in and programme columns (the restated statement differs from the live one by exactly two lines, proven by diff). **Named, not fixed:** `created_at.split('T')[0]` as a plan block's start fallback when `start_date` is null (two lines in `js/app-progress.js`), the dev seed script, and a handful of `new Date(<stored date>)` comparisons and sorts that are off by hours, not a shown day. Found by the release review: `_bucketKey` (chart buckets) parsed a stored date as UTC midnight, so west of UTC a session dated the 1st landed in the month before; fixed with `_dateOnly` and a unit test in three zones. Its WEEK key has an older, separate quirk (the day arithmetic crosses a daylight-saving change, so a date on a week boundary can move a week in some zones, e.g. Auckland); not fixed, not asserted.
