# weekly full-file review (2026-08-09)

**NEW — weekly full-file review (2026-08-09): 7 write functions in app-progress.js write client 1RMs/personal-bests/weight-history/weight-goals with ZERO app-level ownership anchor.** Full-file security pass over the 3 highest-churn modules (app-runner.js, app-workouts.js, app-progress.js — same review that found and fixed the `discardRunner()` timer leak below). `save1RM`/`delete1RM` (app-progress.js:208-249), `savePerformanceLog`/`deletePerfLog` (:533-569), `saveWeightLog`/`saveWeightGoals`/`deleteWeightLog` (:840-895) all either update/delete `.eq('id', someId)` with no `client_id`/`coach_id` check anywhere, or insert `client_id: clientId` straight from an unverified parameter. Confirmed by reading the actual code, not inferred. **This codebase has an established, hard-won fix for exactly this shape** — `saveRunnerSession` (app-runner.js:2423) and `_verifyTemplateOwnership` (app-workouts.js:2523) both look up and verify the record's real owner before writing, with an explicit comment that the unverified version was "confirmed exploitable via a live cross-tenant probe, 2026-07-30." These seven functions are the only remaining write paths in the three reviewed files that don't follow that convention. **Not yet confirmed exploitable in production** — no RLS SQL is tracked in this repo, so it's possible (but unverified) that Postgres RLS on `client_1rms`/`performance_logs`/`weight_logs`/`clients` already blocks a cross-tenant write independently, the same way it did for the `workout_template_exercises` gap below. Needs the same live 2-account probe used for that 2026-07-30 incident before deciding whether this is a real hole or defense-in-depth-only. Also flagged, lower severity: `openWorkoutLog` (app-runner.js:3097) reads a full session by `id` alone with no anchor (read, not write); `saveExerciseToTemplate` (app-workouts.js:1906) is missing the `_verifyTemplateOwnership` call its sibling functions all have; `moveTemplateExercise` (app-workouts.js:1255) reorders by `id` alone. — ✅ **PROBED LIVE 2026-08-10 — ALL FOUR TABLES CONFIRMED RLS-SAFE. Defense-in-depth only, not a live hole.** This is the probe the row above asked for. `tests/health-data-write-rls-2026-08-10.spec.js` attacks a real client's health data from BOTH untrusted directions — an unrelated coach who owns nothing (PT2), and a REAL client of the same coach attacking a DIFFERENT client (a client writing their OWN health data is legitimate; cross-client is the question). Every operation is attempted RAW, bypassing the app, so it tests the POLICY rather than the app's own guards, and each is probed separately because sql-safety is explicit that a working INSERT does not imply UPDATE or DELETE. **16 attempts, all refused, 0 rows affected every time:** `client_1rms` UPDATE/DELETE/INSERT, `performance_logs` DELETE/INSERT, `weight_logs` DELETE/INSERT, and `clients` UPDATE (the tenancy table `saveWeightGoals` writes to by id with no anchor). Read back as the owning coach: the victim 1RM still reads 100 not 999, the performance and weight rows survive, nothing was injected against that client, and the clients row was not hijacked. **So the seven unanchored functions are hardening-in-depth, not an exploitable gap** — the same verdict reached for `workout_template_exercises`, `client_1rms` INSERT, `exercises`, `goals` and `weight_logs` in earlier probes, and unlike `workout_logs` (2026-07-30) and `events` (2026-08-02), which were genuinely exploitable. Permanent regression test added so a future policy change cannot silently reopen any of the four. **Still worth adding the anchors eventually** — this codebase's own convention (`saveRunnerSession`, `_verifyTemplateOwnership`) is to verify ownership app-side regardless, and the GDPR exposure here (special-category health data) argues for belt and braces — but it is now a known-safe cleanup, not an incident.
