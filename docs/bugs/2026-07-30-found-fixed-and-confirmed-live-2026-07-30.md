# FOUND, FIXED, AND CONFIRMED LIVE 2026-07-30

✅ **CRITICAL — FOUND, FIXED, AND CONFIRMED LIVE 2026-07-30 — `workout_logs`' INSERT and UPDATE policies had no ownership check between `client_id` and `coach_id`.** Confirmed exploitable via a live 2-account test: an unrelated coach (owning zero clients) inserted a `workout_logs` row against another coach's real client — via the app's own JS (a sloppy `clientRecord?.coach_id || currentUser.id` fallback) AND via a raw insert bypassing the app entirely, proving the RLS policy itself had the gap, not just careless app code. The fabricated session would have been visible to the real client in their own history. Root cause, once Jake pulled the real policy definitions: **`"coaches manage own workout logs"` was a single `cmd=ALL` policy checking only `coach_id = auth.uid()`** — covering SELECT/INSERT/UPDATE/DELETE with no client_id check at all. Its UPDATE-specific sibling (`"Coach updates own workout logs"`) had the identical gap, meaning a coach could also re-point one of their own *real* logs onto a client they don't own. **Fixed in full**: JS side (`saveRunnerSession`/`saveWorkoutSession` now refuse to save instead of defaulting `coach_id` on a failed ownership lookup, red→green tested) + SQL side (`scripts/fix-workout-logs-insert-policy-2026-07-30.sql`, split the ALL policy into a coach-SELECT policy plus tightened INSERT and UPDATE policies, each requiring `client_id` to belong to a client the writer actually owns). **A first draft of the SQL had its own bug** — an unqualified `coach_id` inside the policy's subquery that resolved against the wrong table and would have silently rejected every SOLO workout save — caught by 2 independent review agents before it reached Jake. Jake ran the corrected SQL, pasted back the real `pg_policies` output confirming all 5 policies landed exactly as intended, then confirmed a real workout still saves. **Confirmed by Jake, closed.** Still flagged, not yet investigated: `workout_log_exercises`/`workout_log_sets` reasoned-but-not-independently-probed as safe (they anchor via the parent `workout_logs.coach_id`, which is now itself correctly anchored) — worth a direct probe next time this area is touched.
