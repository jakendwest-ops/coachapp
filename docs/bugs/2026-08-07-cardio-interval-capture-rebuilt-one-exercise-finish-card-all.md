# cardio/interval capture rebuilt: one exercise-finish card, all 4 metrics, plus a shared quick-prefs popover

✅ **FIXED + LIVE 2026-08-08 (`bbc2bc0`) — cardio/interval capture rebuilt: one exercise-finish card, all 4 metrics, plus a shared quick-prefs popover.** Supersedes the "proposed direction" below — Jake reversed the pace/stroke-rate deferral same day ("these toggles... need to be inn the builder and runner so that the user can toggle on the fly") and scoped it live via AskUserQuestion: per-session toggle (not account-wide Settings), captured **once when the exercise finishes** (not per-round, not phase-complete), all 4 metrics (HR avg/max, watts, pace, stroke rate) in scope. **Built:** `renderCardioCaptureCard` (app-runner.js) — one shared card, 3 call sites converge on it (`_finishIntervalExercise`, `logRunnerSet`'s hitTarget branch, `startIntervalTimer`'s zero-tick), all of which used to transition away from a finished cardio exercise silently, underneath the very overlay that caused this report. Which metrics get asked for is a per-device `localStorage` toggle (`_cardioCaptureToggles`), shared with a **new quick-prefs icon+popover** (`_openQuickPrefsPopover`, app-core.js) now reachable from the runner AND the builder (`openProgram`/`openTemplate` headers) — this also gives the existing metric/imperial units toggle (previously Settings-only since 2026-07-25) the same on-the-fly reach Jake asked for. Old always-visible-but-occluded `wr-cardio-avg-hr`/`-max-hr`/`-watts`/`-pace` inputs and every dead read site removed — one writer now, not two racing on call order. **2 new migrations run live**: `pace_500m_secs`/`stroke_rate_spm` (both smallint, nullable, sanity-bounded) on `workout_log_sets` — verified via Jake's own `information_schema` query before any JS shipped. **Multi-agent review (3 angles) caught 2 real issues, both fixed same session**: pace-bounding only clamped the upper end, so an out-of-range value (e.g. "0:15") would have failed the whole session's batched insert, not just that field — now silently dropped if out of range, matching every other optional capture field; and the new card had lost the old inputs' placeholder hint showing the coach's prescribed HR-zone/watts target while typing — restored (`tgt.hrZoneMin/Max`/`wattsMin`, same lookup the pre-Start card used). 59 feature tests + full suite 349 passed / 5 pre-existing `client-workout.spec.js` failures (unchanged baseline) / 1 pre-existing flake (unrelated) / 2 skipped. Explicitly out of scope this pass (see plan): progress-chart wiring for pace/stroke-rate; `skipToNextExercise` (early-bail) doesn't route through the capture card yet — flagged as a fast-follow. — (orig) **NEW — cardio HR / watts capture is invisible during an interval session: the inputs render UNDERNEATH the interval timer overlay.** Jake, 2026-08-07, asked for a new feature — "for cardio workouts (skierg etc) i would like the runner to let a user record some data from their session... average: HR, pace, stroke rate, watts". **Investigation found 3 of the 4 already ship** (`avg_hr`/`max_hr` since 2026-07-19, `avg_watts` since 2026-07-23; inputs `wr-cardio-avg-hr`/`-max-hr`/`-watts` at `app-runner.js:884/889/894`, rendered UNCONDITIONALLY for cardio, captured at :1064/:1081/:1436/:1459, persisted at :2337-2339). Jake confirmed via AskUserQuestion he has **never seen them**. Root cause identified from his own screenshot + the code's own comment at `app-runner.js:1457`: *"HR + watts inputs stay mounted **beneath the interval overlay**"* — his SkiErg work is prescribed as INTERVALS (`metric_type:'interval'`, e.g. "Extensive Lactate Threshold Intervals", 2 × 20:00 / 5:00), and for an interval exercise the fullscreen timer overlay covers those inputs for the entire workout. Data path is correct and saves fine; the fields are simply unreachable while training. **This is a discoverability/UX defect on a SHIPPED feature, not a missing feature** — same class as the 2026-07-19 "vs last session" block Jake reported as never-built when it was only invisible (les-046). **Genuinely missing, DEFERRED by explicit reasoning:** stroke rate (no runner input, no DB column — needs a migration) and pace — **reversed above, 2026-08-08.**
